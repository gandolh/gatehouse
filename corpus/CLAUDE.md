# corpus: wiki and work tracker for Gatehouse

This folder tracks work as numbered briefs, the way the owner's other repos do (the corpus-flow
skill), and keeps the wiki: what was decided and why. It was started on 2026-11-24, before any
code, from a grill and a sketch round on 2026-11-23.

Write everything here for a stranger: no secrets, no machine paths, no domain, no usernames, no
personal details.

## Layout

```
corpus/
  CLAUDE.md       this file
  index.md        the front door; its catalog is generated by `bash corpus/lint.sh --index`
  routing.md      which skill runs the work, which layer answers which question
  lint.sh         health check; exits non-zero on failure
  .planned-roots  top-level folders the briefs have yet to create (the lint's allowlist)
  log.md          chronological record, newest last, absolute dates
  briefs/         numbered work specs: todo/ blocked/ done/ superseded/
  wiki/           the synthesis pages; status.md says where the work stands, per area
```

## Retrieval budget

Read `index.md` first and triage on the summary lines, then open at most two or three wiki pages.
Don't read `briefs/` wholesale: `wiki/status.md` says where each area stands.

## Briefs

- A brief is `briefs/todo/<NN>-<slug>.md`, headed `# Task NN: <title>`, then **Depends on**,
  **Runs before** and **Builder** lines, then the sections Context, Files you OWN, Files you must
  NOT touch, Steps, Acceptance, Owner steps and Owner decisions. NN is the highest number across
  `todo/`, `blocked/`, `done/` and `superseded/` plus one, two digits.
- Numbers never change. Finished work moves to `briefs/done/` with the same number and a short
  outcome note added at move time; after that the file is not edited. Work undone later moves to
  `briefs/superseded/` with a one-line note on top.
- Each finished brief gets a `log.md` entry and updates its area's line in `wiki/status.md`.
  Durable findings and decisions get a wiki page.
- Until the first deploy, a finished brief ends on the board at Done, unless it says otherwise:
  nothing can deploy before vps-deploy has a Gatehouse stack.
- Code comments don't cite brief numbers ("brief 03", "(brief 05)"). Say what the code does and
  why; the history belongs in `log.md`.

## Wiki

- Every wiki page opens with `summary:` and `updated:` frontmatter, uses standard relative links,
  and stays under 200 body lines. After adding a page or changing a summary, run
  `bash corpus/lint.sh --index`, then `bash corpus/lint.sh`.
- A decision goes in `wiki/decisions.md` only if it is hard to reverse, surprising without
  context, and a real trade-off with named alternatives. Changing one needs an explicit revisit
  and a `log.md` entry. Glossary entries are definitions with an `_Avoid_:` line.
- Absolute dates only.
- Other repos are named, never pathed: "vps-deploy", "Ward" (the `wzd_auth` repo), "Lantern".

## When sources disagree

1. The code wins over any wiki claim. Check a path or function before acting on what a page says.
2. A brief in `done/` wins over the wiki until the wiki catches up.
3. `wiki/decisions.md` wins over `wiki/status.md` for choices nobody has revisited.
4. For the page's look: the decisions and the briefs, then `design/` in the order its README gives.

The repo-wide rules (no secrets, no CI, no pushes, no deploys) and the brief-board section are in
the root [CLAUDE.md](../CLAUDE.md).
